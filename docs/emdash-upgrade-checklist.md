# EmDash upgrade checklist

Coffer relies on some EmDash behavior that isn't a documented promise. Before moving `emdash` (or `@emdash-cms/plugin-cli`, `@emdash-cms/plugin-test`) to a new version in `plugin/`, `theme/` or the dev site, go through this list. Run the full suites (`cd plugin && pnpm test`, `cd theme && pnpm test`) and `scripts/dev-e2e.mjs` on the dev site, and check each item. Add an item whenever Coffer comes to rely on another such behavior.

| What Coffer relies on | Why it matters | How it's checked |
| --- | --- | --- |
| **`requestMeta.geo` is null off Cloudflare Workers.** EmDash sets it only from Cloudflare's `cf` object, never from `CF-*` headers (spec change 35) | Coffer refuses Cloudflare-hosted sites by `geo !== null`. If an upgrade filled it on Node (for example from `CF-IPCountry` behind Cloudflare's proxy), **every Node site would be refused** | `plugin/tests/routes/platform.test.ts`: the two tests through EmDash's own request handling (one with `CF-*` headers). Also read EmDash's `extractRequestMeta` and `extractGeo` in the new version |
| **The Cloudflare runner's limits:** 10 bridge calls per plugin invocation, CPU about 0.5 to 1 s (phase 07 spike) | Release 1 is Node-only because of the 10-call limit. If an upgrade raised it, or made bridge calls stop counting, spec change 35's option A could be smaller, or the refusal could go | Rerun `spikes/cf-runner/drive.mjs` on a Cloudflare test site, if one exists then; read EmDash's sandbox docs and changelog |
| **`getPublicPluginApiRouteHandler`** in `emdash/plugin-utils`, with the signature `(pluginId, method, path, request)` and public routes only | The theme's pay page and `isPaid` read `status` in-process through it | `theme/` tests; the pay page on the dev site |
| **`getPublicOrigin(url, config)`** in `emdash/api/route-utils` (in the package's `exports` and typed, but not in EmDash's docs; checked 2026-11-02): `config.siteUrl`, then `EMDASH_SITE_URL` or `SITE_URL` (read once and cached), then the request's own origin. It's the same function EmDash's CSRF check on plugin routes uses (`astro/middleware/auth.mjs`, `checkPublicCsrf`) | The theme's tip endpoint accepts an `Origin` equal to it (RT-20, `theme/src/tip.ts`, `crossSite`). If it moved, was renamed, or its order changed, tips behind an https-ending proxy would be refused again, or an `Origin` EmDash itself refuses could pass | `theme/` tests (the three `[T17] [RT-20]` tests); `grep -n getPublicOrigin` in the new `dist/api/route-utils.d.mts` and `public-url-*.mjs`; the tip button through the tunnel on the built copy |
| **Block Kit admin pages load once and never poll** (spec change 27) | The "Checked at" line and the Check again button exist because of it. If EmDash added a refresh, they could go | Read the admin page renderer's changelog |
| **`ctx.site.url`** is `siteUrl` (or `EMDASH_SITE_URL`, `SITE_URL`), then the Site URL setting (`site:url`, https or loopback http), then the setup address (`emdash:site_url`) (EmDash 1.2.0 #3744; spec changes 23 and 42) | The install command's site address uses the admin's browser origin when EmDash's is loopback or missing, which still happens on a site set up under `npm run dev` with neither of the first two set. If EmDash stopped falling back to the setup address, or changed the order, the page's wording and the fallback need another look | `plugin/tests/routes/admin-site.test.ts`; on an upgrade, read `readSiteInfo` and `resolveSiteOrigin`, and load the dev site's admin page (no `siteUrl`, setup address `http://localhost:4321`: the red banner, or the browser's https origin when there is one) |
| **Headers set by a component are lost; only the page file's are sent** (Astro, phase 06 session 6c) | `preparePayPage` must run in the page file | `theme/tests/paypage.test.ts` and the dev site's built copy (`curl -I`) |
| **Plugin storage pages are at most 100 rows** (spike). `getMany` and `deleteMany` take any number of ids since EmDash 1.2.0 (#3776); on 1.1.0 they failed above about 98 on D1 | The watch scan pages by 100. Coffer's batches of 98 or fewer are no longer needed since the 1.3.1 floor; they stay as they are (removing them is optional cleanup) | `plugin/tests/store.test.ts` |
| **Block Kit renders every text as plain text:** React children, no `dangerouslySetInnerHTML`, no markdown or links (`@emdash-cms/blocks` 1.1.0, checked in phase 07 session 7b) | Tip notes, written by visitors, are shown as given in the admin page | `plugin/tests/routes/admin-tips.test.ts` keeps notes unchanged in the blocks; on an upgrade, grep the new `@emdash-cms/blocks` for `dangerouslySetInnerHTML` and markdown rendering |
| **EmDash skips its editor toolbar on a page that already has an element with `id="emdash-toolbar"`** (its dedupe marker in the request-context middleware, 1.1.0 to 1.4.0; since 1.2.0 #3681 it injects only before a whole document's `</body>`). EmDash 1.3's opt-in `toolbar: "client"` mode instead adds an inline bootstrap script to every public page; the pay page's CSP blocks it, and it also stops when `#emdash-toolbar` is there | The pay page and the tip endpoint's pages carry an empty `<div id="emdash-toolbar" hidden>` so the toolbar isn't added there; our CSP would block it. If the marker changes, the toolbar comes back unstyled for editors (harmless) | `theme/tests/paypage.test.ts` and `tip.test.ts` check the placeholder; on an upgrade, read `injectToolbar` and `injectBeforeBodyEnd` in EmDash's middleware, and the client bootstrap's check; fetch the pay page signed in (one `id="emdash-toolbar"`, no bootstrap) |
| **A storage cursor saved under one EmDash version still works under the next** | The purge keeps its `query` cursor in KV between cron runs (`plugin/src/housekeeping.ts`), across an upgrade. A cursor that stopped decoding would stall or restart the purge | On an upgrade, read the storage cursor's decoding. 1.3.0 (#3885) adds sort values to cursors; a cursor without them, as 1.1.0 wrote, falls back to looking up its anchor row |
| **`ctx.kv.getVersioned` and `ctx.kv.compareAndSet`** (in `KVAccess` since 1.3.1; the floor is 1.4.0 now): a conditional write on a revision applies for one of two requests that read the same revision, and every write changes the revision | The pairing code is claimed with it, so only one of two simultaneous pair requests wins (RT-07, spec change 50). If the write stopped being conditional, both would pair again | `plugin/tests/redteam/sync.test.ts` "[T13] [RT-07] C6: two pair requests…" on the test host (the real KV through the sandbox bridge); live: `node scripts/redteam/round2-live.mjs c6` on the dev site |
| **Storage paging by `(created_at, id)` stays cheap when rows have their own `created_at`:** each 100-row page of a `query` is its own SQL query, ordered by `(created_at, id)` after the cursor (EmDash 1.3.1 and 1.4.0; RT-15, spec change 51) | The watch scans read up to 20,000 rows a sync and nothing but that row cap bounds their time. On 1.3.1 and on 1.4.0 a sync over a 20,100-row flood takes about 1.1 s on the built copy; a paging change could put it near the Node runner's 30 s wall, where every sync fails and settlement stalls | **Fails above 5 s a sync.** Back up `data.db`; with the site stopped, `node scripts/redteam/backlog-live.mjs seed --shape flood --count 20100`; build and start the built copy on loopback (CLAUDE.md, the H1/L7 row); `node scripts/redteam/backlog-live.mjs time --site http://127.0.0.1:4322 --max-ms 5000`; stop it and restore the backup. Never time the default `settled` seed: its rows share one `created_at` and take 27 s |

The five items from the 1.4 release notes:

- **The flood-seed timing run:** the paging row above. No change.
- **Caching (#4243):** only pages that use EmDash's cache hints lose Astro's implicit `no-cache`. The pay page and the tip endpoint use none and set `Cache-Control: private, no-store` themselves, and `theme/` already tests it on each kind of response: the pay page found and unknown (`paypage.test.ts`), the tip endpoint's 303 and its fallback pages (`tip.test.ts`), and its error pages (`redteam.test.ts`, `[T23]`). No test was missing. Built copy: the pay page (404) and a refused tip POST (400) both carry it. The site's own post pages are the site owner's.
- **Deferred tasks (#4394):** it covers content, taxonomy and comment writes and publication hooks. Coffer has `content:read` only and its one content call (`ctx.content.get` in checkout) is awaited; no Coffer test inspects an after-hook, so none needs `host.waitForDeferredTasks()`. The suites pass unchanged.
- **Bundle check:** the note above was wrong about what changed. `emdash-plugin bundle --validate-only` built the plugin before validating in 0.13.4 too (the same `buildPlugin` call in both versions), so CI's "Bundle caps" step and the commit rule mean what they did: they check a fresh build of the committed source. What did change is `@emdash-cms/plugin-test` 0.2.11 (#4273): the test host builds in a temporary folder and no longer writes `plugin/dist/`. So `pnpm test` leaves `dist/` alone, and the dev site needs `pnpm run build` after a source change, as the commands table already says.
- **DOMPurify:** cleared in our dev tree, by its own lockfile commit on 1.3.1 before the EmDash bump (`698272d`): `dompurify` 3.4.16 to 3.4.17 in `plugin/` and `theme/`; the dev site had 3.4.17 already. `pnpm why dompurify` after: 3.4.17 ← `@emdash-cms/admin@1.4.0` ← `emdash@1.4.0`. **This clears our dev tree only.** `@emdash-cms/admin@1.4.0` still asks for `^3.3.2`, so a site gets whatever its own lockfile resolved; moving to EmDash 1.4.0 doesn't by itself move it off 3.4.16.

Also checked: RT-12 (accepted limit) is unchanged. The canary's 60 s spin was stopped at 30,051 ms and a `status` request alongside it waited 30,039 ms (1.3.1: 30,045 and 30,033). The canary's 15 isolation probes gave the same picture as in round 1, with the same two "allowed" (plain http to an allowed host; undeclared `ctx` APIs present, their writes refused). `@emdash-cms/sandbox-workerd` 0.9.6's built code is identical to 0.9.5's.

Not covered: the Cloudflare runner's limits (read only); the tip button through the tunnel on the built copy (a tip was made from the Welcome post on the dev site in `astro dev` during the live step, and left unpaid).

The live stagenet tip: `e140` (0.002 XMR, index 360), created on the dev site with the installed bridge syncing and paid by Wyatt from the Feather buyer wallet. Seen at 0 confirmations at 20:17 UTC, 1 at 20:20, settled at 2 by 20:30 (2026-11-14). The admin page lists it as settled.
